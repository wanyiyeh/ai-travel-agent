## 0. 原則與範圍

- **表單上每個選項，都要對應到演算法真的做得到的事。** 做不到的就不放，或者交給自由文字。
  現在的「人數」就是反例：它在 `src/` 裡完全沒有被讀取。
- 只改**規則引擎路徑**，也就是 `assembleItineraryDays` → `itineraryCityGen` 的 `*ViaScheduler`。
  舊的全 LLM 流程只是失敗時的 fallback，只同步更新 `buildPreferencePrompt` 的文字。
- 每個選項的表單 UI 跟著它的演算法同一個階段上線，不先放一個還沒作用的選項。

## 1. 最終表單設計

### 1.1 版面

| 位置 | 欄位 |
|---|---|
| 最上方 | **國內／國外** 切換（國內的設計見 1.10，在階段 5 實作；之前只有國外） |
| 外層（不收合） | 出發／抵達城市、日期、**步調**、**預算**、**＋加入固定行程**、旅遊風格描述 |
| 「更多選項」（收合） | 航班時間、**出門時間**、**飲食限制**、**偏好**、**飲品**、**室內行程為主**、**同行者**、**交通方式** |

「人數」移除，改成「同行者」。後端 `TripPreferencesSchema.travelers` 保留選填，因為舊行程的 config 裡還有這個值。

### 1.2 步調：用停留時間區分

每天的景點數不再固定 4 個，改成從出門時間開始排到 18:00，排得下幾個就排幾個。
停留時間依景點類型決定：

| 停留時間類別（`DurationCategory`） | 緊湊 | 適中 | 悠閒 |
|---|---|---|---|
| `museum`（博物館、美術館） | 90 分 | 180 分 | 210 分 |
| `park`、`shopping` | 60 分 | 150 分 | 180 分 |
| `viewpoint`、`temple`、`landmark` | 45 分 | 120 分 | 150 分 |
| 其他類型 | 60 分 | 150 分 | 180 分 |
| 一天大約排得下 | 最多 6 個（上限） | 2～3 個 | 2～3 個 |

2026-10-04 實作時用 `dev.db` 的 44 個景點池（529 個景點）驗證：地標 38%、寺廟 19%、公園 15%、
博物館 12%、購物 8%、觀景台 7%。原本的表（地標類在適中只停 60 分）會讓適中一天排到 4～5 個、
緊湊約 8 個，跟「適中大約 3 小時」的定義不符，所以把地標類也拉長（選項 B），緊湊另外設每天最多 6 個。

表單說明改成描述停留時間，例如「緊湊：每個景點約 1.5 小時內」，不再寫景點數。

### 1.3 預算

| | 經濟實惠 | 中等消費 | 高端奢華 |
|---|---|---|---|
| 住宿 | 青旅 | 民宿、約三星級飯店、東橫 Inn 這類平價商務旅館 | 希爾頓、萬豪等級的國際品牌飯店 |
| 午餐、晚餐（每人） | 平價小館、外帶；優先推薦 NT$400 以下 | 優先推薦 NT$1,000 以下 | 優先推薦 NT$1,000～3,000（原定 2,000，評分後放寬，見下方） |
| 早餐、點心 | 不設上限 | 不設上限 | 不設上限 |

「優先推薦」的排序：價格符合的排最前面，查不到價格的排中間，超出預算的排最後。

2026-10-06 依評分腳本（`npm run eval-form-fidelity`）的結果調整：
- 高端的午晚餐上限從 NT$2,000 放寬到 NT$3,000：東京的高級晚餐多半 ¥10,000 起（約 NT$2,100），原本的上限幾乎全部排除。
  高端另外用 Text Search 的價位篩選查高價位餐廳（Nearby 依熱門度排序的池子裡幾乎都是拉麵、咖哩）。
- 經濟實惠的住宿改成「平價住宿類型」（青旅、民宿、平價旅館、汽車旅館）有 3 間以上就只交給 AI 這些，青旅排最前面；
  只看青旅時數量常常不到 3 間，AI 就挑了四星級的淺草豪景飯店。
  搜尋也只查平價類型，不再混入泛用的 `lodging`（混入時淺草熱門前 20 間全是連鎖飯店，沒有平價住宿可篩）；
  平價住宿不到 3 間時（例如小鎮），才另外查一般住宿，排在後面。
- 東京的住宿和餐廳依預算在不同區域查（`stayAreas.ts`）：經濟實惠淺草／上野、中等與未選新宿、高端銀座／丸之內；景點以東京車站為中心。
因為很多店家沒有價格資料，這是排序，不是過濾。

### 1.4 偏好（可複選）

| 偏好 | 內容 | 位置 |
|---|---|---|
| 美食 | 市場、農夫市集；牧場、農場（酒莊、啤酒廠移到 1.8 的「酒」） | 市區；郊區（半日或一日遊） |
| 文化歷史 | 博物館、美術館、古蹟 | 市區 |
| 自然景觀 | 公園、植物園、觀景台、海景 | 市區，輕鬆看風景 |
| 水上活動 | 海灘、碼頭、水上樂園、海釣 | 多半在郊區，要判斷季節 |
| 陸上活動 | 國家公園、步道、極限運動、滑雪 | 郊區，要判斷季節 |
| 購物 | 紀念品店、市場、超市、商場、outlet | 市區（outlet 多半在郊區） |
| 影劇追星 | 拍攝地朝聖，選了之後多一個選填欄位「想朝聖的作品」 | 都有可能 |

排法規則：
- **選了多個偏好時，每天一個主題輪流排**。每天另外保留 1～2 個一般熱門景點，
  每天的標題也寫出主題，例如「京都文化巡禮」。
- **郊區的一日遊和半日遊**：一個城市待 3 天以上才排 1 個一日遊；待 2 天最多排半日遊；只待 1 天不排。
  **只有選了自駕才排郊區的一日遊**（見 1.7）。

### 1.5 同行者（可複選）：獨旅／親子／長輩／寵物

都不選就是一般旅遊。選了多個時規則會疊加，例如「親子 + 寵物」就是住宿要可以帶狗、
餐廳優先推薦適合兒童又可以帶狗的店。**寵物只在國內旅遊時顯示**（見 1.10）。

**獨旅跟親子、長輩互斥**（選了一邊，另一邊變成不能點）；獨旅可以跟寵物同時選。

選了親子之後：
- 景點加入親子類型。
- 餐廳優先推薦適合兒童、有兒童餐的店。
- 陸上活動不推薦難度高的步道。
- 經濟實惠的住宿不推薦青旅，改推薦民宿。
- 每天 17:00 前結束。
- 表單上的「酒」（1.8）藏起來不顯示。

選了長輩之後：
- 步調預設偏悠閒，每天早一點結束。
- 不推薦登山步道、極限運動；優先推薦有無障礙入口的地點（Google 的 `accessibilityOptions`）。
- 景點之間盡量減少轉乘和長距離步行。
- 經濟實惠的住宿不推薦青旅。

選了寵物之後（只有國內）：
- **住宿只推薦可以帶狗的**（Google 的 `allowsDogs`）。住不進去整趟就失敗了，所以這是過濾，不是排序。
- 餐廳優先推薦可以帶狗的。
- 景點加入狗公園 `dog_park`、寵物咖啡廳 `dog_cafe`；行程資訊附上附近的動物醫院 `veterinary_care`。
- 高鐵、台鐵規定寵物要裝籠或提袋，所以交通方式預設自駕。
- Google 只有「狗」的欄位，帶貓或其他寵物時只能參考住宿介紹，表單上要說明這個限制。

選了獨旅之後：

Google 沒有「適合一個人」的欄位，獨旅大多靠景點類型和 AI 挑選時的指示來近似，可靠程度比親子、寵物低。

| 項目 | 做法 |
|---|---|
| 餐廳 | 優先推薦一個人吃也自在的類型：`ramen_restaurant`、`noodle_shop`、`food_court`、`sushi_restaurant`、速食。挑餐廳的 prompt 請 AI 避開要兩人以上才能點的店（雙人套餐、大份量火鍋） |
| 住宿 | 經濟實惠：青旅、`budget_japanese_inn`；中等消費：商務旅館（單人房多）。膠囊旅館、商務旅館沒有類型，用文字搜尋 |
| 住宿位置 | 優先推薦離車站近的（已有「最近車站」資料） |
| 晚上的行程 | 21:00 前回到住宿附近；選了「酒」時，小酌推薦離住宿走路就到的店 |
| 推薦旅遊團 | 用文字搜尋當地的一日遊團、步行導覽（用 `minRating` 參數過濾，維持 Pro 計費），**以建議清單呈現，不直接排進行程**，因為旅行社的資料品質不好控制 |
| 花費試算 | 住宿無法分攤，用單人價格計算 |

### 1.6 出門時間、飲食限制、自由文字

- **出門時間**：早起 8:00 前出門（排程用 07:30）／一般 09:00／晚起 11:00 後出門（排程用 11:00）。
  排程已經支援（`START_TIME_MINUTE`），但現有的值（早起 07:00、晚起 10:00、沒選時 08:00）要改成這組，
  沒選時的預設也改成 09:00。
  - 出門越晚，當天能排的景點越少：例如晚起 + 適中，11:00～18:00 扣掉午餐，大約只排得下 2 個。
  - 晚起時早餐時段改推薦早午餐（`brunch_restaurant`），或者不排早餐。
- **飲食限制**（可複選）：素食、純素、不吃海鮮、不吃牛、清真、不吃辣。
  標籤沿用 `parsePreferenceIntent` 的寫法：`vegetarian`、`vegan`、`no_seafood`、`no_beef`、`halal`、`no_spicy`。
- **旅遊風格描述**：改成多行的 textarea。placeholder 改成引導使用者寫按鈕表達不了的事，
  例如「一定要去清水寺、不想排太多購物」。表單上已經有的選項，不再當成範例。

### 1.7 交通方式（單選）：大眾運輸／自駕

自駕指的是**到當地再租車**，第一版只做「整趟都租車」：從抵達機場取車，開到回程機場還車。

| 項目 | 自駕 | 大眾運輸 |
|---|---|---|
| 郊區一日遊 | 照 1.4 的規則排 | **不排郊區一日遊**，只排市區和半日遊。表單提示「想去郊區景點，建議選擇自駕」 |
| 景點之間的交通 | 一律用開車時間 | 跟現在一樣，依距離選步行或大眾運輸 |
| 導航連結 | 開車路線 | 大眾運輸路線 |
| 住宿 | 優先推薦有停車場的（Google 的 `parkingOptions`） | 優先推薦離車站近的（已有「最近車站」資料） |
| 第 1 天 | 抵達後先到機場取車（Google 的 `car_rental` 類型可以查到租車公司） | — |
| 最後一天 | 預留還車時間，到機場的時間比原本提早約 30 分鐘 | — |
| 提醒 | 第 1 天提醒國際駕照或駕照譯本；抵達和回程城市不同時，提醒會有甲租乙還的費用 | — |
| 喝酒 | 「小酌」時段只推薦**從住宿走路就到得了**的店；酒莊、啤酒廠照排，但介紹裡提醒「駕駛不能試飲」 | — |

之後可以考慮：只有部分天數租車（例如市區搭電車、到郊區才租車），以及沒有車時改推薦當地的一日遊行程（tour）。

### 1.8 飲品（可複選）：咖啡／抹茶、茶／酒

飲品放在**餐點時段**，不是景點：

| 選項 | 放在哪裡 | 怎麼找 |
|---|---|---|
| 咖啡 | 取代「點心」時段；早餐也優先推薦咖啡專門店 | `coffee_shop`、`coffee_roastery`、`coffee_stand`，加上文字搜尋「specialty coffee」「pour over」 |
| 抹茶、茶 | 取代「點心」時段 | `tea_house`、`tea_store`，加上文字搜尋「matcha」 |
| 酒 | 晚餐後**新增「小酌」時段**，優先推薦離住宿近的店 | 市區：`bar`、`wine_bar`、`cocktail_bar`、`pub`、`beer_garden`、`brewpub`；郊區：`winery`、`vineyard`、`brewery`（半日或一日遊，照 1.4 的規則） |

- 同時選了咖啡和抹茶時，點心時段每天輪流。
- Google 沒有品質欄位，用這幾個方式近似「好喝、有特色」：文字搜尋的關鍵字、Text Search 的
  `minRating` 參數（Google 在伺服器端過濾，不用要評分欄位，維持 Pro 計費），
  並排除連鎖店（星巴克、路易莎、麥當勞等，名單放在常數裡）。
- 清酒酒藏、威士忌蒸餾廠沒有專屬類型，要用文字搜尋。
- 同行者選親子時，「酒」藏起來（1.5）；交通方式選自駕時的規則見 1.7。

### 1.9 室內行程為主（獨立勾選項）

說明文字：「不想曬太陽、下雨也能玩」。它會調整所有偏好的排法，不是一種景點主題，所以不放在偏好清單裡。

Google 沒有「室內或戶外」的欄位，依景點類型判斷，對照表放在常數裡：

| 分類 | 類型例子 |
|---|---|
| 室內 | 博物館、美術館、水族館、商場、百貨、天文館、室內遊戲場、溫泉、茶館 |
| 戶外 | 公園、步道、海灘、國家公園、動物園 |
| 看情況 | 寺廟、觀景台（例如晴空塔是室內的） |

勾選之後：
1. 室內景點優先排。
2. **11:00～15:00 盡量排室內**；戶外景點如果還是排到了，放在早上或傍晚。
3. 景點之間距離較遠時，交通改用大眾運輸，減少走路曬太陽。
4. 跟戶外偏好（自然景觀、水上活動、陸上活動）同時選時，**戶外活動照排**，但套用第 2 點，避開中午。

之後可以考慮：每個戶外景點旁邊附一個「下雨時可以改去」的室內備案。

### 1.10 國內旅遊（台灣境內）

國外 = 從台灣出國；國內 = 在台灣旅遊。步調、預算、偏好、飲品、同行者、飲食限制、出門時間的規則國內外共用，
差別在於下面這些：

| | 國外 | 國內 |
|---|---|---|
| 目的地怎麼選 | 選機場（`AIRPORTS` 表） | 選城市或地區，例如台南、花蓮、墾丁 |
| 怎麼到目的地 | 飛機 | 開車、高鐵、台鐵、客運 |
| 第一天、最後一天 | 依航班抵達、起飛時間 | 依出發時間、預計回到家的時間 |
| 自駕 | 到當地租車（取車、還車、國際駕照、甲租乙還） | 開自己的車，不用取車還車，也不用相關提醒 |
| 高端住宿 | 國際品牌飯店 | 國際品牌加上台灣的高級飯店（晶華、老爺等，名單放在常數裡） |
| 專屬偏好 | 影劇追星 | **夜市、老街、溫泉、露營** |
| 專屬同行者 | — | **寵物** |

國內專屬偏好怎麼找：

| 偏好 | 怎麼找 |
|---|---|
| 夜市 | 沒有專屬類型，用文字搜尋「夜市」。排在晚上，可以取代晚餐 |
| 老街 | 沒有專屬類型，用文字搜尋「老街」 |
| 溫泉 | 文字搜尋「溫泉」，搭配大眾浴場 `public_bath`、`spa` 類型 |
| 露營 | 露營區 `campground`、露營小屋 `camping_cabin`，加上文字搜尋「露營」。露營可以當成當晚的住宿 |

### 1.11 固定行程（演唱會、球賽、表演、訂位、工作等）

使用者自己填日期、時間、地點，排程把那段時間**鎖住**，其他行程繞著它排。
「影劇追星」（拍攝地朝聖）維持是一般偏好；演唱會追星用固定行程處理，兩者分開。

**表單**：「＋加入固定行程」按鈕，可以加多筆，每一筆填：
- 類型：演唱會／球賽／表演／餐廳訂位／**工作（商務會議、遠距工作）**／其他
- 日期：只能選在旅程期間內
- 開始時間、結束時間（選填；演唱會預設 3 小時）
- 地點：直接輸入場館名稱。**不用 Google 自動完成**（每打一個字都可能計費），生成時再用 Text Search 查一次並快取。
  類型是「工作」時地點選填，沒填就當成**在住宿工作**，不另外查詢

類型是「工作」時（接住商務順道遊、遠距工作的旅客，見第 6 節）：
- 每天可以各加一筆，例如每天 14:00～17:00 開會，其他時段照常排景點。
- 沒填地點時，那段時間排在住宿，前後的景點優先選離住宿近的。
- Google 沒有 WiFi、插座的資料，所以**不推薦**「適合工作的咖啡廳」；要找共享空間，使用者可以自己填
  （Google 有 `coworking_space` 類型，屬於 Pro 計費，之後要推薦也做得到）。

**排程規則**：
- 固定行程的時段鎖住，不被其他景點佔用，重新排時間時也不會動到它。
- 多城市行程：場館所在的城市，當天一定要排在那個城市。`planTrip` 分配城市天數時當成條件，分配完再檢查一次，
  不符合就重試或報錯。

**類型是演唱會時，額外安排**：

| 安排 | 做法 |
|---|---|
| 提早到場 | 預設提早 2 小時（排周邊、排入場），使用者可以改 |
| 當天其他行程 | 只排早上的輕鬆行程，下午往場館移動 |
| 晚餐 | 排在場館附近，開場前吃，或散場後吃宵夜 |
| 住宿 | 當晚優先推薦場館附近的 |
| 回程交通 | 散場時間接近末班車時提醒使用者 |

偶像相關景點（經紀公司大樓、聯名咖啡廳、生日應援廣告）資訊變動快，AI 容易給出過時的資料，**先不做**，
讓使用者寫在自由文字裡。

### 1.12 季節亮點（依出發日期自動安排）

表單不用新增日期欄位，用既有的出發日期判斷。加一個**預設勾選**的「加入季節限定景點」，不想要的人可以取消。
季節亮點會成為某一天的主題，例如「京都賞楓日」，跟其他偏好的主題日一起輪流排。

季節亮點要看地方，不能只看月份：同樣是 1 月，東京幾乎不下雪、札幌有雪祭、雪梨是夏天、曼谷是涼季。
所以分三層判斷：

1. **季節**（純計算）：出發月份 + 目的地緯度 → 南北半球、是否熱帶 → 春夏秋冬，熱帶則是乾季／雨季。
2. **季節亮點**：AI 依城市和日期列出亮點（例如 11 月京都的嵐山、東福寺），再用 Text Search 確認地點存在並快取，
   跟影劇追星同一套做法。AI 不知道今年的實際花期，介紹文字要保守，例如「通常在 11 月中下旬最美」。
3. **氣候資料確認**：用 [Open-Meteo](https://open-meteo.com/) 的免費歷史天氣資料，查這個城市往年同期的
   平均氣溫和降雪量，過濾掉不合理的推薦（例如東京的賞雪）。不需要 API key；免費方案限非商業用途，
   作品集專案符合，**商業化前要改用付費方案**。

季節也會影響每天怎麼排：

| 狀況 | 調整 |
|---|---|
| 冬天天黑得早 | 依日期和緯度算日落時間（純計算）。戶外景點排在日落前，日落後改排夜景或室內 |
| 夏天很熱 | 中午盡量排室內，跟「室內行程為主」（1.9）共用邏輯 |
| 雨季（日本 6 月梅雨、東南亞季風季等） | 提高室內景點的比例 |

**1c-2. 依用途分開計費級距（省錢，2026-10-04 定案並完成）**

Google 依請求裡最貴的欄位計費（Pro：每月免費 5,000 次；Enterprise：每月免費 1,000 次）。
目前所有 Nearby Search 都帶 `rating`／`priceLevel`，全部按 Enterprise 收費。改成只有真的需要價格的查詢才用 Enterprise：

| 查詢 | 級距 | 原因 |
|---|---|---|
| 景點池（`tourist_attraction` 與之後的偏好池） | **Pro**：拿掉 `rating`、`priceLevel` | 排程不用評分，改用 Google 回傳的熱門排序（`rankPreference: POPULARITY`）；景點幾乎都沒有 `priceLevel`（`dev.db` 確認過），門票估算本來就退回預設值 |
| 早餐、點心 | **Pro** | 不設預算上限，不需要價格 |
| 住宿 | **Pro** | 等級靠類型和品牌名稱判斷，不需要價格 |
| 午餐、晚餐 | **Enterprise**：`priceRange`、`priceLevel`、`rating` | 預算門檻要靠價格區間；評分既然不加錢就保留 |

2d-3 演唱會和工作的額外安排（提早到場、場館附近的晚餐和住宿、末班車提醒、工作日的景點靠近住宿）。2d-1 的決定：
- 時間軸上是 📌 特別的景點，顯示訂好的時間，不能「換一個」，可以刪除。
- 餐廳訂位取代那一餐：11:00～15:00 取代午餐、17:00 以後取代晚餐、其他時間取代點心；不會多排一家餐廳。
- 沒填結束時間時：演唱會、球賽 3 小時，表演 2.5 小時，餐廳訂位 1.5 小時，其他 2 小時；工作一定要填結束時間。
- 當天其他景點在鎖住的時段前後照常排，景點數依剩下的時間自動減少。
- 場館用 Text Search 在城市附近查一次（Pro，快取 30 天，找不到也記住）；查不到就保留使用者輸入的名稱。
- 場館不會再被排成當天或之後的一般景點（例如東京巨蛋演唱會那天不會又排東京巨蛋觀光）。
- 交通日的固定行程在 2d-1 只會加到當天的行程裡，不重新安排其他景點（多城市在 2d-2 處理）。

2026-10-09 2d-3 的決定（`feat/fixed-event-extras`）：
- 提早到場：表單讓使用者自己選，演唱會預設 2 小時、球賽 1 小時、表演 30 分鐘；提早的時間也鎖住，其他景點排在它之前。
- 晚餐：演唱會、球賽、表演在 16:00～21:00 開場時，晚餐換成場館 800 m 內的餐廳（每個場館多查 1 次 Nearby，Pro），
  時間軸上排在演出前；使用者自己訂了晚餐就保留訂位。
- 住宿不換；場館離住宿超過 10 km 時，在固定行程上提醒「散場回住宿較遠」。
- 散場晚於 22:30 時提醒留意末班車（固定門檻，不查路線）。
- 工作：當天景點本來就依離住宿的距離評分，不另外處理。

- 每個選到的偏好，每個城市各多查 1 次 Nearby Search（快取 30 天），併進候選池：
  - 文化歷史：`museum`、`art_museum`、`art_gallery`、`historical_place`、`historical_landmark`、`monument`
  - 自然景觀：`park`、`garden`、`botanical_garden`、`observation_deck`
  - 購物：`gift_shop`、`market`、`supermarket`、`shopping_mall`、`department_store`
  - 美食（市區）：`market`、`farmers_market`、`food_court`
- `mapPlaceTypeToCategory` 把新類型對應到停留時間類別，有需要就新增類別，並補上 1.2 的三種步調時間。
- 主題輪流排：依天數把偏好分配給每一天，每天保留 1～2 個 `tourist_attraction` 熱門景點。
- 每天的標題改成寫出主題。
- 取代原本的 `INTEREST_CATEGORY_BOOST` 1.5 倍加權。
- 飲品（1.8）：
  - 咖啡、抹茶：點心時段改用飲品的候選池，連鎖店名單過濾、`minRating` 過濾（維持 Pro）。
  - 酒：`DayMeals` 新增 `drinks`（小酌）時段，`MEAL_TYPES`、`dayTimeline.ts`（排在晚餐後）、
    `MealTimelineRow`、`MealPicker`、`meals/[mealType]/regenerate` 都要支援。
  - 文字搜尋「specialty coffee」「matcha」需要能回傳**多筆**結果並快取。現有的 `placesTextSearch`
    只取最符合的一筆，所以要另外做多筆版本，記得接 `googleFetch` 和快取。
- 室內行程為主（1.9）：
  - 新增室內／戶外對照表，跟 `mapPlaceTypeToCategory` 一樣依 Google 類型判斷。
    要等這個階段把景點類型擴充好之後才判斷得出來，所以放在這裡。
  - 排程：室內景點加權；`assignTimeSlots` 排時間時，戶外景點避開 11:00～15:00。
  - 交通：遠距離改用大眾運輸。
  - 表單新增獨立勾選項，附說明文字。
- 固定行程（1.11）：
  - 跟主題日一起做，因為兩者都在決定「每一天怎麼分配時間」。可以拆成獨立的 PR（`feat/fixed-events`）。
  - `TripPreferencesSchema`（或另開欄位）新增 `fixedEvents: { type, date, startTime, endTime?, venueName }[]`。
  - 排程：現有的「鎖定一整天」（`isLocked`）和 restructure 的「保留必去景點」都不能指定時段，
    要讓 `assignTimeSlots` 能接受一段固定的時間，其他景點排在它前後。
  - `planTrip`：把「某天必須在某城市」當成條件寫進 prompt，回傳後檢查，不符合就重試。
  - 演唱會的額外安排照 1.11 的表；末班車提醒先用固定門檻（例如散場晚於 22:30 就提醒），不另外查 Routes API。
  - 場館用 `placesTextSearch` 查（有快取），查不到時保留使用者輸入的名稱，不擋生成。
  - 「工作」類型：地點選填，沒填就排在住宿；同一天前後的景點優先選離住宿近的。

### 階段 3：郊區的半日遊和一日遊、交通方式、季節（`feat/day-trips`）

交通方式決定了要不要排郊區的一日遊，所以跟這個階段一起做。

- 郊區類型的搜尋半徑放寬到 50 公里：
  - 陸上活動：`national_park`、`state_park`、`hiking_area`、`adventure_sports_center`、`ski_resort`
  - 水上活動：`beach`、`marina`、`water_park`、`fishing_charter`
  - 美食（郊區）：`farm`、`ranch`
  - 酒（郊區）：`winery`、`vineyard`、`brewery`；選了自駕時介紹裡提醒「駕駛不能試飲」
- 一日遊和半日遊的規則照 1.4。一日遊沿用「鎖定一整天只排一個景點」（`isLocked`）的機制。
- 季節判斷：依出發月份和緯度判斷南北半球，冬天不推薦海灘，非雪季不推薦滑雪場。
  跟下面的季節亮點共用同一個 `src/lib/season.ts`（純函式，有單元測試）。
- 季節亮點（1.12）：可以拆成獨立的 PR（`feat/seasonal-highlights`）。
  - `season.ts`：月份 + 緯度 → 季節；日期 + 緯度 → 日落時間。
  - 氣候資料：Open-Meteo 的歷史天氣 API，每個城市 + 月份查一次，結果存進新的快取表
    （例如 `ClimateNormalCache`）。它不是 Google 的服務，不經過 `googleFetch`；`MOCK_PLACES`
    模式下要另外回傳假資料，避免測試和 `dev:mock` 打到外部服務。
  - AI 列出季節亮點 → 用氣候資料過濾 → Text Search 確認地點（有快取）→ 當成某一天的主題。
  - 排程：戶外景點排在日落前；夏天中午、雨季時提高室內比例。
  - 表單：預設勾選的「加入季節限定景點」。
- outlet 沒有對應類型，用 Text Search「outlet」加上 `shopping_mall` 類型來找。
- `farm` 在 Google 屬於「Business」類別，可能查到不開放參觀的農場。景點池是 Pro 計費、沒有評分資料，
  所以改成只留 `types` 裡同時帶有 `tourist_attraction` 的農場。
- 交通方式（1.7）：
  - 表單新增「交通方式」；只有自駕才排郊區的一日遊。
  - 自駕時，`getDistancesForStopPairs` 一律用開車模式；導航連結帶 `travelmode=driving`。
  - 第 1 天加入取車、最後一天預留還車時間，並加上國際駕照、甲租乙還的提醒。
  - 住宿的 `parkingOptions` 屬於較貴的計費級距，**只在選了自駕時**、而且只在找住宿時才要求（使用獨立的快取鍵值）。

## 6. 其他使用者類型（2026-10-04 外部審閱回饋）

審閱者（Miss June）從決策動機、行為阻力、社交動態的角度，補了 4 種目前規劃沒有直接涵蓋的使用者。
她的提醒也是本計畫的原則：**第一版不要把所有類型都做成表單按鈕**，先用現有的機制接住。
依 MoSCoW 優先順序處理：

| 使用者類型 | 優先順序 | 處理方式 |
|---|---|---|
| 商務順道遊、遠距工作 | **Should**（第一版就做） | 不用新增按鈕：固定行程（1.11）多一個「工作」類型，把開會、辦公時段鎖住，其他時段繞著它排。跟固定行程一起在階段 2 實作 |
| 朋友出遊、團體（3～6 人，一人主揪） | **Could**（下一輪） | 見 6.1 |
| 情侶、蜜月（重視氛圍、拍照） | **Could**（下一輪） | 見 6.2 |
| 打卡特攻（快閃、只拍照） | **Won't（這一版不做）** | 見 6.3 |

### 6.1 朋友出遊、團體

- **痛點**：多人的排隊耐受度、訂位難度跟一兩個人完全不同。熱門拉麵店、只有吧台的小店，5 個人很難同時入座；
  團體自駕還牽涉到車型和行李空間。這也是拿掉「人數」之後留下的缺口。
- **做法**：同行者新增「朋友／多人」。
  - 午晚餐優先推薦 Google 標記為**適合團體**（`goodForGroups`）、**可訂位**（`reservable`）的店。
    這兩個欄位屬於 Enterprise + Atmosphere 級距，比照親子的兒童欄位，**只在選了朋友／多人時**才要求，使用獨立的快取鍵值。
  - 選了自駕時，提醒注意車型大小和行李空間。
- **主揪的溝通成本**：主揪通常要把行程截圖給朋友看、反覆修改。可以做「分享唯讀連結」，
  讓擁有者產生一個連結給朋友看。目前已有公開範例的唯讀機制（`authorizeItineraryRead`，只限管理者），
  開放給一般擁有者時，連結要用無法猜到的 token，並且可以撤銷。這屬於存取控制，**另外開計畫**，不放在這份。

### 6.2 情侶、蜜月

- **痛點**：對「氣氛」很敏感，被排到吵雜的家庭餐廳或快步調的熱門景點，體驗會大打折扣。
  希望有日落景觀、景觀咖啡廳、浪漫晚餐，步調偏鬆但不無聊。
- **目前已經能用組合接住**：自然景觀（觀景台、海景）+ 飲品（咖啡、小酌）+ 悠閒步調，加上季節亮點的日落時間（1.12）。
- **下一輪**：同行者新增「情侶」，挑餐廳的 prompt 加入「氣氛佳、適合約會」。
  Google 沒有「氣氛」的欄位，這部分只能靠 AI 判斷，可靠程度比親子、寵物低。

### 6.3 打卡特攻

- **特徵**：每個點只停 20 分鐘拍照就走，比緊湊的 45 分鐘還短；很在意路線不走回頭路；
  可能 06:00 就出門，比「早起」的 07:30 還早。
- **這一版不做**：目前「緊湊」一天 5～6 個點，對多數人已經夠用。
- **怎麼決定之後要不要做**：上線後觀察自由文字（存在 `config.generatedWith`）裡出現「快閃、特攻、只拍照」的頻率，
  夠多再考慮新增更極端的步調或更早的出門時間。統計時只看彙總的次數，不看個別使用者的內容。
