# 重新規劃行程精靈 — UX 優化計畫

## 背景

`RestructurePanel.tsx`（[src/components/RestructurePanel.tsx](../src/components/RestructurePanel.tsx)）是「重新規劃行程」的單一入口，固定 4 步：

1. **城市／景點** — 加城市、加必去景點、拖曳排序、周邊/順路推薦
2. **天數** — 每個城市用 +/- 調整 `targetDays`
3. **保留/捨棄既有天** — 勾選要保留哪幾天既有內容（城市被縮減時用）
4. **確認套用** — 新增/移除/AI 新規劃的 diff 摘要 + 套用

走這個精靈的使用者，很多時候只是「加一個城市」或「把某城市天數 +1」，跟 Step 3 的「保留/捨棄」完全無關——但現在的設計是不管需不需要都要走滿 4 步。

## 已發現的摩擦點

| # | 問題 | 位置 |
|---|------|------|
| 1 | **Step 3 常態性是空步驟**。只有「既有城市被縮減、且預設保留清單裝不下」時才有實際選擇要做；`defaultKeepIds()` 已經自動選好推薦保留的天，多數情況使用者只是點過去。 | `step === 3` 區塊，[RestructurePanel.tsx:1036-1084](../src/components/RestructurePanel.tsx#L1036-L1084) |
| 2 | **Step 2 調天數看不到具體影響**，要等到 Step 4 才知道「+1 天」实际上是哪一天被加進來、「-1 天」捨棄的是哪個既有的日子。 | `step === 2` 區塊，[RestructurePanel.tsx:975-1033](../src/components/RestructurePanel.tsx#L975-L1033) |
| 3 | **回程日期順延/提前的警告重複出現兩次**（Step 2 跟 Step 4 幾乎同一句話），到 Step 4 已經是看第二遍。 | [RestructurePanel.tsx:990-996](../src/components/RestructurePanel.tsx#L990-L996) 與 [:1137-1142](../src/components/RestructurePanel.tsx#L1137-L1142) |
| 4 | 整體 4 步對多數操作（只是加城市/調天數）而言偏重，實際上只有「真的要縮減既有城市」才用得到完整 4 步。 | 整體流程設計 |

## 決定方向：精簡成 2 步

原本考慮的「Step 3 動態跳過」只是在 4 步框架內的局部修補。討論後決定直接做更大的改動：
把 **城市/景點 → 天數 → 保留/捨棄 → 確認套用** 4 步，合併成 **2 個畫面**，一次解決摩擦點 #1-#3
（#4 的「步驟偏重」本身就是這次改動要解的問題）。

### 新流程

**Step 1（不變）：城市／景點**
維持現狀不動——加城市、加必去景點、拖曳排序、周邊/順路推薦，都不受影響。

**Step 2（新）：調整與確認** — 合併原本的 Step 2(天數) + Step 3(保留/捨棄) + Step 4(diff+套用)

每個城市卡片：
- 天數 +/- stepper（沿用現有 `setTargetDays` 邏輯，[:580-598](../src/components/RestructurePanel.tsx#L580-L598)）
- **即時 diff**：卡片內直接顯示這次調整的結果——保留原本 X 天／移除：第 N 天／AI 新規劃 Y 天／🔒 鎖定景點日。這段邏輯目前寫死在 Step 4 render 裡才算（[:1089-1098](../src/components/RestructurePanel.tsx#L1089-L1098)），改成每個城市隨時可呼叫的衍生值，不用等到最後一步才看到效果——同時解決摩擦點 #2。
- **進階：手動選擇要保留哪幾天**（可展開，預設收合）：只在該城市有既有非結構性天數時才出現（沿用原 Step 3 的篩選條件，[:1041-1042](../src/components/RestructurePanel.tsx#L1041-L1042)），展開後就是原本 Step 3 的 checkbox 清單 + 「還原建議勾選」。

卡片清單下方：
- 總天數摘要 box（原有 vs 套用後天數，[:1123-1136](../src/components/RestructurePanel.tsx#L1123-L1136) 的邏輯搬過來）
- 回程日期警告——**只保留一份**（目前 Step 2 跟 Step 4 幾乎同句話各講一次，[:990-996](../src/components/RestructurePanel.tsx#L990-L996) 與 [:1137-1142](../src/components/RestructurePanel.tsx#L1137-L1142)，合併後自然只剩一份，解決摩擦點 #3）
- 「上一步」（回 Step 1）／「套用至行程」

### 技術方案

1. **型別**：`step` 從 `1 | 2 | 3 | 4` 簡化成 `1 | 2`（[:325](../src/components/RestructurePanel.tsx#L325)）。
2. **Diff 計算抽成函式**：把 Step 4 render 裡的區域變數邏輯（`removed`/`keptCount`/`sightseeingKeptCount`/`addedAiDays`）抽成 `computeCityDiff(city, daysById)`，在新 Step 2 畫面裡對每張城市卡片即時呼叫，而不是只在最後一步算一次。
3. **展開狀態**：每個城市卡片的「進階：手動選擇要保留哪幾天」需要自己的展開/收合 state，例如 `expandedKeepKeys: Set<string>`（跟現有 `expandedBatchIds` 之類 UI-only state 同一種做法），不需要寫進 `CityEntryState`。自動展開只是「初次觸發裁切時把對應 key 加進這個 Set」，使用者之後手動收合要維持收合，不能每次重新計算就把它強制蓋回展開——也就是自動展開只「加」，不「減」，收合永遠是使用者自己點的。
4. **原本 Step 2／Step 3／Step 4 的 JSX** 大致是搬進同一張城市卡片、依序排列，邏輯本身（`setTargetDays`、`toggleKeep`、`resetKeepToRecommended`）不用改，只是渲染位置從「各自一個 step 區塊」改成「同一張卡片裡的小節」。
5. **進度指示**：「第 {step} / 4 步」文字（[:760](../src/components/RestructurePanel.tsx#L760)）拿掉，改成依 `step` 切換的畫面標題（見下方技術決策）。

### 技術決策

| 問題 | 決策 | 原因 |
|------|------|------|
| 「進階：手動選擇要保留哪幾天」預設展開/收合 | 預設收合；只有這次調整會**裁切**既有天（即 `syncKeepDaysForTarget` 實際動到 `keepDayIds`、觸發原本的 cap 邏輯）時才自動展開 | 多數情況不需要使用者操心，但天數被迫犧牲掉時不該悄悄發生，要主動攤開提醒 |
| 是否保留「第 X / Y 步」步驟計數器 | 拿掉，改用畫面標題（Step 1「選城市與景點」→ Step 2「調整與套用」） | 只剩 2 步時，編號計數器傳遞的資訊量太小，標題文字更直接 |

### 待留意

- **卡片視覺密度**：多城市行程（5-6 個城市）時，每張卡片同時有 stepper + diff + 可展開 checkbox，垂直空間會比現在重，需要留意摺疊狀態的預設是否讓畫面保持可掃視。

## 功能整併：表單偏好也要套用到重新規劃

`plan/form-preference-wiring.md` 階段 1～5 的功能都做在生成行程的主流程（`assembleItineraryDays.ts`）。
重新規劃（`restructure/route.ts`）是另一條路，每個城市自己呼叫 `generateDayStops`、`generateMealsAndAccommodation`，
所以只拿到一部分。2026-10-10 盤點：

### 已經有的（不用改）

重新規劃會讀行程存下的表單偏好（`config.preferences`），合併成 `preferenceIntent`、`mealPreferences` 傳下去，所以這些已經生效：
- 步調、出門時間、偏好類別的加權、飲食限制、室內優先；
- 親子、長輩、獨旅、寵物的餐廳和住宿規則（包括寵物只排寵物友善住宿、溫泉飯店優先）；
- 親子、長輩 17:00 結束；
- 國內的移動日（高鐵、台鐵、開自己的車）。

### 缺的

| 功能 | 主流程 | 重新規劃現在 | 影響 |
|------|--------|--------------|------|
| 主題日標題（文化巡禮、親子同樂、老街巡禮、毛孩同樂…） | 每天有主題，標題寫在當天 | 景點有照主題挑，但 `generateDayStops` 只回傳景點，**標題被丟掉**；主題輪替每個城市都從第一個開始 | 新的一天標題只有「探索」 |
| 景點以住宿為中心排路線 | 有 | 沒有，用市中心 | 路線離住宿較遠 |
| 郊區一日遊、半日遊、兩天一夜 | 有 | 沒有 | 把城市加到 3 天以上也不會出現一日遊 |
| 季節限定日、季節過濾 | 有 | 沒有 | 新的日子可能排到不當季的地點 |
| 日落、天氣（雨天室內、熱天午休、`weatherNote`） | 有 | 沒有 | |
| 固定行程（演唱會等） | 依日期排進那一天 | 沒有：天數前後移動後，演唱會那天可能被捨棄或移到別的城市 | **最嚴重**：訂好的行程可能消失 |
| 影劇朝聖日 | 有 | 沒有 | |
| 國內偏好：夜市晚餐、溫泉泡湯、露營 | 有 | 沒有（只有溫泉飯店優先） | |
| 跟團連結（`tourKeyword`） | 一日遊、季節限定日有 | 沒有 | |
| 一日遊的午餐留在當地 | 有 | 沒有一日遊，所以不適用 | |
| 自駕取車、還車 | 第一天、最後一天 | 不適用：重新規劃不會動到第一天和回程日 | — |

### 做法

不在重新規劃裡再寫一次這些規則。把 `assembleItineraryDays` 裡「一個城市的觀光日」那一段抽成共用函式，
例如 `buildCityStayDays(city, days, context)`，包括：
- 主題輪替；
- 一日遊和半日遊；
- 季節、天氣；
- 固定行程、影劇、夜市、溫泉、露營；
- 住宿和三餐。

主流程和重新規劃都呼叫它。這樣以後新增功能只要改一個地方，不會再出現「主流程有、重新規劃沒有」。

重新規劃要多傳給它的資訊：
- 這個城市的新日子在整趟行程的**第幾天、哪個日期**：季節、天氣、固定行程都要靠日期；
- 前面已經排過的主題數：主題輪替接著排；
- 整趟已經用過的地點：不重複；
- 整趟已經排過的一次性項目（露營一晚、影劇朝聖日）：不重複排。

### 精靈畫面要配合的地方

- **Step 2 的即時 diff**：「AI 新規劃 Y 天」改成列出每天的類型，例如「AI 新規劃 3 天（含一日遊 1 天、季節限定 1 天）」。
  實際內容要套用後才知道，所以這裡只說「會依偏好排」，不預先保證，
  例如「待 3 天以上會排一日遊」。
- **固定行程的日子一定保留**（2026-10-10 決定）：有固定行程（演唱會、訂位等）的那天，跟移動日、回程日一樣不能被捨棄。
  城市縮短時，保留清單先放這天，「進階：手動選擇要保留哪幾天」裡這天的勾選框不能取消，旁邊標「🔒 演唱會」。
  - 怎麼認出這天：用表單存下的 `preferences.fixedEvents`（有日期、地點），對到當天裡 `fixedEvent` 的那個景點。
    不能只看景點有沒有 `fixedEvent`，因為租車取車、還車和國內的去程、回程也有。
  - 想取消固定行程，就到表單把它刪掉，不在精靈裡處理。
- **固定行程的日期會跑掉**：保留下來的天會依新的順序重新編號。如果在它前面加了城市或加了天數，演唱會那天的日期就會往後移，
  例如從 11/12 變成 11/13，但票上的日期不會變。Step 2 要警告「演唱會（11/12）會變成第 N 天（11/13），跟票上的日期不同」，
  請使用者調整前面的天數。這裡只警告，不自動調整。
- **偏好不在精靈裡改**（2026-10-10 決定）：精靈沿用行程原本的表單偏好。想換偏好就重新生成行程。

## 驗證

1. Step 1 加完城市按「下一步」直接進 Step 2，標題顯示「調整與套用」（不是「第 X / Y 步」），看到每個城市卡片都有 stepper + diff 文字。
2. 調整某城市天數 +/-，卡片內的 diff 文字即時更新，不用跳頁才看到。
3. 把某個既有城市天數調到會裁切既有天（觸發 cap）→「進階：手動選擇要保留哪幾天」自動展開；手動取消勾選某天 → diff 文字同步更新。
4. 調天數但沒有觸發裁切（或單純新增城市）→「進階」區塊維持收合；若使用者自己手動展開過，再調整天數不應該又被強制收合回去。
5. 對一個單純新增/沒有既有非結構性天數的城市：確認該城市卡片完全不出現「進階」區塊（跟現在 Step 3 的篩選條件一致）。
6. 回程日期警告只出現一份，不是兩份重複文字。
7. 從 Step 2 按「上一步」回到 Step 1，資料不遺失（城市/景點/天數都還在）。
8. `npx tsc --noEmit`、`npm run lint`、`npm test` 全過。
