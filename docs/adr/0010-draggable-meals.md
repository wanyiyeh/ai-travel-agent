# ADR-0010：午餐、點心、晚餐可以在當天拖拉，位置存成「前面有幾站」；餐點可以刪除

日期：2026-10-27
狀態：Accepted

## 背景

餐點沒有自己的時間，`buildDayTimeline`（`src/lib/dayTimeline.ts`）依規則插入：午餐在第一個 `afternoon` 的站前面，點心與晚餐固定在所有景點之後。使用者拖拉之後，`assignTimeOfDay`（`src/lib/scheduler/assignTimeSlots.ts`）依「第幾站 ÷ 總站數」重新分配時段，所以：

- 午餐的位置只由站數決定，4 站的一天永遠在第 2、3 站之間
- 景點排不到晚餐之後，例如晚餐後再去看夕陽、夜景（#287，原本回報成 #289）

餐點也沒辦法刪除，只能「換一家」；不想吃點心的人，點心永遠佔著一個位置。

## 決策

- **午餐、點心、晚餐可以在同一天裡拖拉**，放到任兩站之間；不能拖到別天。早餐固定第一、小酌固定最後。
- 每一餐的位置存在 day 上的 `mealPositions`，例如 `{ lunch: 2, snack: 3, dinner: 3 }`，意思是「這一餐前面有幾站」。沒有設定的餐沿用現在的規則，所以新生成的行程不受影響。拖過一次之後，三餐的位置一起存。
- **拖拉的結果就是放開時畫面上的順序**：拖景點跨過餐點，景點就排在餐點的另一邊，餐點的位置跟著重算。
- **餐點的先後不能對調**：午餐 → 點心 → 晚餐。拖到違反順序的位置時，放開後退回，並提示可以先移動擋住的那一餐，或把它刪除。兩餐之間可以沒有景點。
- **每一餐都可以刪除**：從 `meals` 移除，並記在 day 上的 `skippedMeals`，畫面上不再顯示它的空位，也不佔順序；當天底下顯示「加回點心」，按了會變回「選擇點心」的空位。
- 時段依餐點分段：午餐前的站是上午，午餐到晚餐之間是下午，晚餐之後是晚上。地圖路線共用 `buildDayTimeline`，順序自動一致。

## 考慮過的替代方案

- 每一站可以手動選上午、下午或晚上，餐點跟著時段走：使用者要先理解「餐點跟著時段走」，比直接拖餐點難懂。
- 存「接在哪一站之後」（stop id）：拖走那一站時餐點會跟著跑；那一站被刪除時還要另外處理。
- 拖景點時餐點留在原位（前面的站數不變）：拖拉過程中餐點會讓位，放開後又跳回去，看到的跟得到的不同。
- 違反順序時自動把擋住的餐點一起推走：使用者沒有要求移動那一餐，結果難以預料。
- 刪除餐點只是把 `meals` 的那一格清空：清空的格子會顯示成「選擇點心」，仍然佔著順序。
- 早餐與小酌也可以拖：早餐拖到下午這類結果不合理，需求也沒有出現過。

## 後果

- day 多兩個欄位：`mealPositions`、`skippedMeals`。day 自己的欄位不經過 `src/lib/placeStorage.ts` 的白名單，不用另外登記。排序 API 可以一起儲存 `mealPositions`。
- 新增刪除與加回餐點的 API；挑選餐點時也會把那一餐從 `skippedMeals` 拿掉。
- 拖拉的範圍多了一種「只能在當天移動」的項目，`handleDragOver` 與 `handleDragEnd` 要區分景點與餐點。
- 重新計算交通改用 `mealPositions` 分配時段，不再只看站數。只移動餐點、景點順序沒變時，由排序 API 直接重排時段，不重新計算交通，也就不呼叫 Routes。
- 交通的文字仍是「從上一個景點」算起，不是從餐廳算起，維持現狀。
- 晚上的固定行程（演出前先吃晚餐，`isDinnerBeforeStop`）在使用者沒拖過晚餐時沿用原本的規則；拖過之後以使用者的位置為準。
