# ADR-0014：「重新規劃行程」改由聊天進入，精靈在聊天版驗收後刪除

日期：2026-11-24
狀態：Accepted

## 背景

「重新規劃行程」精靈（`src/components/RestructurePanel.tsx`，約 1,300 行）要使用者一步步調整城市順序、天數、保留哪些天、鎖定哪些必去景點。使用者想把功能收斂：需要描述意圖、做取捨、要好幾步的操作交給聊天助理（[PLAN-004](../plans/PLAN-004-itinerary-chat.md)），不再維護兩套入口。

後端的 `src/app/api/v1/itinerary/[id]/restructure/route.ts` 本來就接受結構化的最終結果（城市、是否新城市、天數、保留的天、鎖定的景點），跟前端的操作步驟無關。

## 決策

- 聊天助理把「京都多待一天，大阪改成一天」轉成城市清單提案。提案卡顯示前後差異，並寫明哪些天會重新產生、原內容會進垃圾桶。使用者確認後，呼叫既有的 restructure 端點。新城市的推薦接既有的 `transit-recommendations`。
- restructure 端點保留，行為不變。
- 精靈先保留。聊天版的重新規劃通過驗收、使用者用手機實際測過之後，另開 PR 刪除精靈的前端（#365）。
- 一個動作就能完成的操作保留按鈕，聊天也能做：拖拉、刪除、換一間、垃圾桶。

## 考慮過的替代方案

- **兩種入口永久並存**：使用者可以自己選，但兩套 UI 都要維護，產品也不夠聚焦。
- **這次就刪除精靈**：程式碼最少，但聊天版出問題時就沒有可用的重新規劃入口。
- **聊天只負責把精靈的表單填好**：精靈仍是主要介面，維護成本沒有降低。
- **所有按鈕都收進聊天**：拖拉、刪除用按鈕比打字快，垃圾桶是聊天改壞時的安全網，所以保留。

## 後果

- 精靈會把選項攤開給人看，聊天不會。聊天面板要有建議問題按鈕（例如「調整城市天數」「加一個城市」）。
- 重新規劃會重新產生好幾天，也會查 Google、花錢。提案卡一定要清楚列出影響範圍，確認後沿用 restructure 原本的額度。
- 鎖定必去景點要靠伺服器端比對名稱，因為 LLM 看不到 Google 名稱（[ADR-0013](0013-chat-server-side-authorization.md)）。
- 如果 Haiku 5.5 常誤解重新規劃的要求，這一類可以單獨改用 Sonnet 5.5，不影響其他類別。
- 刪除精靈後，glossary 的「重新規劃」、功能頁與 `architecture.md` 要改成以聊天為入口。
